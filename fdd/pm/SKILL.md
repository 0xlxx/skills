# FDD PM — 需求与规约

## 职责

厘清"要做什么"。核心产出是 **API 签名 + 类型定义 + 验收标准**。不写实现，不写测试。

设计 API 时遵循 [api-design](../api-design/SKILL.md) 原则：渐进式增强、框架无关、DX 优先、原子化。

**流程**：

```
PM 出规约（API 签名 + 类型）
    ├── Dev 实现 ──────────────┐
    └── Test 写测试（可并行）──┘  → Dev 跑测试 → 修复循环 → 全绿
```

## 输入

- 上游参考源码（如 ELK Java 实现）
- 用户描述的功能目标
- 项目现有代码结构

## 核心产出：API 规约

**API 签名即规约主体**。Dev 照着实现，Test 照着写测试。双方基于同一份类型，无需翻译。

### API 规约模板

```ts
// 输入
interface XxxOptions {
  /** 必填：... */
  key: Type;
  /** 可选：...（默认 xxx） */
  optional?: Type;
}

// 输出
interface XxxResult {
  key: Type;
}

// API 签名
function featureName(options: XxxOptions): XxxResult;
```

### API 设计检查

设计 API 时逐条对照：

- **渐进式**：新手只传必填参数就能跑，高级场景通过可选参数解锁
- **框架无关**：核心不依赖 React/Vue 等框架，如有框架绑定抽成适配器
- **DX**：命名符合直觉、默认值覆盖 80% 场景、TypeScript 类型自动推断
- **原子化**：拆分正交的原子 API，不做能调参的巨无霸

### 验收标准

每个 API 对应若干验收标准：

```md
- [ ] 标准 1：正常输入 → 预期输出
- [ ] 标准 2：可选参数省略 → 使用默认行为
- [ ] 边界：空输入
- [ ] 边界：极端值
- [ ] 边界：错误输入 → 行为明确
```

### 范围限定

- 本次不做：...

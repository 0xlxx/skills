# 校对：同音串字

听写的错误高度集中在**同音串字**——模型听对了声音，写错了字。知道错误长什么样，校对就从「逐字读」变成「定点搜」。

## 错误模式（真实例子）

| 模式 | 实际 | 听写成了 |
|---|---|---|
| 英文技术词 → 汉字 | `mihomo` | 米红木 |
| 英文参数被听成短语 | `no-resolve` | 弄水造物 |
| 英文词被听成大写字 | `nftables` | InfTables / NFTBOS |
| 协议名被听成常用词 | `QUIC` | Quick |
| 人名/品牌音近 | 七尺宇 | 七日宇 |
| 数字丢位 | 443 端口 | 43 端口 |
| IP 被重复 | 8.8.8.8 | 8.8.8.8.8.8.8 |
| 术语双写 | 出站 | 初战 |
| 口语被直译 | 敲下回车 | 悄悄回摔 |
| 一句被拆碎或合成长段 | 带标点的长句 | 无标点长段 |

## 校对流程

1. **先建词表。** 来源：标题、视频简介、章节表、配套配置或代码仓库、官方文档。词表同时用于第二遍听写和校对。
2. **定点搜可疑项。** 英文词、缩写、数字、端口、IP、人名——这几类错了最伤引用价值。
3. **两版对照。** 第一遍和第二遍不一致的位置就是要重点看的位置；两版都一样的地方也未必对，但优先级低。
4. **找外部锚点验证。** 官方文档、仓库里的配置文件、章节标题都能证伪一个猜测。例：`disable-qtype-65` 的语义要去 mihomo 官方文档确认，而不是照口语猜。
5. **标记不确定。** 听不清或语义存疑的片段，在交付里点名，而不是抹平。
6. **记录改动清单。** 每个改动写「原文 → 改成 → 依据」。使用者要能复核你的判断。

## 校对边界

- **保留口语与语气。** 听写稿的价值在于它是原话；顺手润色会丢掉演讲者的措辞和重点。
- **核对每一个数字。** 端口、版本号、参数值错一位，整段结论就反了。
- **只写音频直接支持的内容。** 推断出来的部分标成「推断」并写下依据。
- **标注版本来源。** 素材 URL、时长、转录日期、模型名一并给出，后来人才能判断能不能引用。

<tourist>

<core-principle>
不是炫技，不是堆高级数据结构——是用**最直接**的方法，以**最小常数**通过。tourist 的优化哲学：降维——将复杂问题回归本质，用基础工具（DFS、线段树、二分、分块）打到编码极限。一切为 AC 和运行效率服务。
</core-principle>

<step>
先识别瓶颈，再动手——分析当前代码的时间/空间复杂度、常数来源、缓存行为。
完成标志：能一句话说出"这段代码慢在哪里"（hot path、复杂度项、常数来源）。
</step>

<rules>

### 1. 常数优先——基础优化做到极致

**直觉：** O(N) 大常数不如 O(N log N) 小常数。理论复杂度是上界，实际跑的是常数。

**做法：**
- 循环内不分配内存——全局扁平数组，一次 `new` 或 `vector::reserve`，复用
- 位运算替代集合操作——`std::bitset` 或 `uint64_t` 做状态压缩，`__builtin_ctz/clz` 加速
- 缓存友好——按行遍历矩阵、struct-of-arrays 替代 array-of-structs
- 减少分支——把 `if` 提出循环，用查表替代条件跳转

**反面：** 循环内 `vector.push_back`、`unordered_map` 临时构造、为"代码清晰"牺牲布局

```
// ❌ 循环内分配
for (int i = 0; i < n; i++) {
    vector<int> tmp; tmp.push_back(a[i]); ...
}
// ✅ 预分配复用
vector<int> tmp; tmp.reserve(n);
for (int i = 0; i < n; i++) { tmp.clear(); tmp.push_back(a[i]); ... }

// ❌ bool vis[N] 逐个检查
// ✅ uint64_t mask 一次判重
```

### 2. 根号平衡——复杂结构是最后选择

**直觉：** 线段树是 O(log N)，但常数大、代码长、容易写挂。√N 分块虽然渐进更差，但常数极小、代码极短、几乎不出错。当 N ≤ 2e5 时，√N ≈ 450，分块的实际运行时间往往和线段树同级甚至更快。

**做法：**
- 区间查询/修改优先考虑分块或莫队，而非树套树、Link-Cut Tree
- 调块大小——理论 √N，实际用 N / √(Q) 或 N / √(Q log N) 往往更快
- 能用前缀和 + 差分解决的绝不上数据结构

**反面：** 一上来就写线段树、平衡树、树剖——复杂度对但常数吃光收益

```
// ❌ 线段树（40行，常数 4×）
// ✅ 分块（15行，常数 1×），N=2e5 时实际更快
for (int bid = l / B; bid <= r / B; bid++) {
    if (bid == l/B || bid == r/B) { /* 暴力跑边界块 */ }
    else { ans += block_sum[bid]; }  // 整块 O(1)
}
```

### 3. 降维——隐式结构替代显式指针

**直觉：** 指针 = 间接访问 = cache miss。数组隐式存储消除指针追逐。

**做法：**
- 线段树用数组隐式索引——`tree[i*2]`、`tree[i*2+1]`，无用 `new node()`
- DP 用滚动数组——高维 DP 只保留前一层状态，`dp[2][N]` 替代 `dp[N][N]`
- 图用邻接表数组——`vector<int> g[N]` 或 CSR 格式，非 `vector<Edge*>` 
- 状态用整数压缩——位运算编码多维状态，替代 `map<tuple<...>>`

**反面：** 指针二叉树、`dp[N][M][K]` 三维全部保留、`map<vector<int>, ...>` 做 DP 记忆化

```
// ❌ int dp[N][N] → 4e10，内存爆炸
// ✅ int dp[2][N] → 只留前一行
for (int i = 0; i < n; i++) {
    int cur = i & 1, prev = cur ^ 1;
    for (int j = 0; j <= W; j++)
        dp[cur][j] = max(dp[prev][j], j>=w ? dp[prev][j-w]+v : 0);
}
```

### 4. 打表找规律——暴力跑小数据，推公式降维

**直觉：** 很多"算法题"其实是数学题。先写一个纯暴力 DFS/BFS 跑 N ≤ 10，印出前几项，观察规律——可能直接得到递推公式或封闭解，复杂算法退化到 O(1) 或 O(N)。

**做法：**
- 写暴力跑 N ≤ 10 或 N ≤ 20，输出序列
- 观察——是否线性递推？是否组合数？是否常数？OEIS 搜索
- 规律找到 → 预计算 + 每组 O(1) 回答
- 即使没找到完美公式，预计算能大幅减少实时计算量

**反面：** 上来就写复杂 DP 或网络流，N=1e5 时 TLE 才发现有 O(1) 公式

```
// 问：N 个节点的二叉树有多少种形态？
// 不推 DP → 暴力跑 N=0..5: 1,1,2,5,14,42
// 认出 Catalan 数 → ans = C(2n,n)/(n+1) → O(1)
```

### 5. 够用就停——最直接的方案就是对的

**直觉：** tourist 的模板只有极少的 `#define` 和 `using`。不为了学术新潮引入重型抽象——每个抽象都带来常数和认知开销。尝试不同的方法，停在最直接的那个。

**做法：**
- 优先标准库——`std::sort`、`std::nth_element`、`std::priority_queue`，不自造轮子
- 宏只做键盘节省——`#define fi first`、`#define se second`，不做逻辑宏
- 写完问自己：能不能删掉一层抽象？能不能用更朴素的结构？
- 一个方案写完，如果代码超过 50 行，回头想有没有更短的路

**反面：** 模板元编程、继承层次、为"可扩展性"引入虚拟接口——在竞赛场景全是负收益

# Patterns

用于设计或 review 等待、反馈、模态、撤销、拖放、搜索和新手引导。每个 pattern 都先确认它是否真的有必要；Apple HIG 的大方向是减少打断、保留上下文、让用户可预测地恢复。

## Loading

### HIG 思想

- 理想状态是加载快到用户没有意识到等待；不要长时间显示空白或冻结界面。
- 尽早显示可理解的内容或稳定占位，再逐步替换为真实数据。
- 加载不应阻塞用户完成其他独立任务；能后台处理就后台处理。
- 明确表达“正在加载”和“大约需要多久”；已知进度用 determinate，未知进度用 indeterminate。
- 不要只用一个覆盖全页的旋转器，除非任务确实是全局或不可分割的。

### Web 做法与校验

- UI 立刻回应操作：本地 pending 状态、按钮 disabled/进度的组合要避免用户重复提交。
- 加载时间很短时避免闪烁；超过短暂瞬间再显示持久加载态，具体阈值按产品和网络测试。
- 优先使用局部 skeleton、流式内容、增量加载或乐观更新；结构占位应与最终布局相近，减少跳动。
- 使用 `aria-busy`、状态文本和 live region 配合；不要只让屏幕阅读器读到一个转圈图标。
- 已知总量用 progress；未知总量用 spinner/不确定进度。进度不能假装精确。
- 长任务支持取消、重试、后台继续、刷新后恢复；离线/超时要区分状态。

### Review 问句

- 用户等待时是否看得见任何有意义的反馈？
- 加载完成后页面是否发生严重跳动、焦点丢失或输入被清空？
- 离开再回来时，任务状态是否仍可理解？

## Feedback

### HIG 思想

- 反馈要帮助用户知道当前状态、动作结果、下一步可能做什么，以及在出错时如何纠正。
- 反馈强度要匹配事件重要性：普通状态用低干扰、就地反馈；数据丢失、不可逆风险才需要打断。
- 警告意外且不可逆的数据损失；不要对用户已经预期的结果反复警告。
- 重要任务完成时可以有确认，但常规成功通常只需自然的状态变化。
- 命令无法执行时，说明原因并给出可执行原因或下一步，而不是只说“失败”。

### Web 做法与校验

- 就近反馈优先于全局 toast：字段错误贴近字段，行状态贴近行，保存状态贴近保存动作。
- 多通道表达：颜色/图标/文本/动画/声音至少搭配一种非颜色方式；不要让声音成为唯一反馈。
- toast 适合短暂、非关键、可忽略的信息；明确错误、需要决策或可能丢失数据的内容应使用持久区域或 dialog。
- 错误要保留输入、定位到问题、提供修改动作，并避免提交后清空表单。
- `aria-live` 只用于真正需要播报的变化；频繁状态更新要合并或静默，避免屏幕阅读器被噪音淹没。
- 成功反馈和错误反馈使用稳定位置、稳定语气和一致术语。

### Review 问句

- 用户做完动作后，能否立即知道发生了什么？失败后能否继续？
- 反馈是否出现在用户视线和操作上下文附近？
- 关键错误是否被埋在一个会自动消失的 toast 里？

## Modality

### HIG 思想

- 只在有明确收益时使用模态：需要聚焦、确认、做短决策或完成一个边界清楚的任务。
- 模态任务应短、简单、线性；不要在一个模态里再造完整应用和深层导航。
- 必须有明显退出方式；如果关闭会丢失内容，要在关闭前解释并提供保存/放弃/继续编辑。
- 一次只显示一个主要模态；不要多个 modal、sheet、alert 相互覆盖。
- 模态标题应说明任务，让用户知道自己暂时离开了原来的上下文。

### Web 做法与校验

- 优先使用原生 `<dialog>` 或可靠的 dialog 组件；Popover 不等于 modal，不能自动继承模态语义。
- 模态打开时隔离背景交互；关闭后恢复焦点和滚动位置。URL/历史是否需要变化要明确，不要让 Back 行为不可预测。
- `Esc`、关闭按钮、外部点击和取消按钮的语义一致；破坏性确认不能把“取消”和“删除”做成同样突出的默认动作。
- 使用 `aria-labelledby`/`aria-describedby` 建立标题和说明；避免焦点逃出 dialog。
- 移动端需要处理软键盘、视口高度和 safe area；不要固定高度导致操作按钮不可达。
- 模态结束后的结果要反馈到原上下文，用户不必重新寻找位置。

### Review 问句

- 这个任务真的需要阻断其他内容吗？页面内展开是否更合适？
- 退出、保存、放弃、返回分别做什么，是否可从界面预测？
- 关闭 modal 后用户是否回到原来的焦点和内容位置？

## Undo and Redo

### HIG 思想

- 用户需要能预测撤销/重做的目标，并在结果不可见时得到高亮、滚动或说明。
- 允许多次撤销；不要让用户做两步后就必须重新开始。
- 相关的小改动可批量撤销，或提供逻辑还原点。
- 只有必要时才提供专用按钮；系统/约定快捷键和菜单优先级更高。
- 不要让撤销吞掉用户后来想到的其他工作，也不要把浏览器 Back 和 Undo 混淆。

### Web 做法与校验

- Web 编辑类产品至少考虑 Cmd/Ctrl+Z、Shift+Cmd/Ctrl+Z（或产品约定的 Redo），并在 UI 中显示可理解的“撤销 X / 重做 Y”。
- 对删除、移动、批量修改、拖放和自动保存提供可理解的历史记录；撤销后显示结果位置。
- 创建、删除、重命名、权限变更等操作的历史边界要定义清楚；不要把不可逆的外部副作用伪装成可撤销。
- 可用短暂的 inline undo action，但不要让用户必须抓住自动消失的 toast。关键工作应能在历史/版本中找回。
- 浏览器 Back 只负责导航历史；页面内的编辑历史应单独管理，必要时允许两者共存。

### Review 问句

- 用户能否知道下一次撤销会改变什么？
- 撤销后是否有可见结果和历史反馈？
- 用户误操作为什么不能恢复？是产品设计还是技术限制？

## Drag and Drop

### HIG 思想

- 拖放适合移动、复制、排序和把内容放入目标容器；不能成为唯一操作方式。
- 同一容器内的拖放通常表示移动，不同容器/应用之间通常表示复制；产品需要提供可预测的规则。
- 支持多选、批量拖放和取消；拖动过程中应提供足够反馈。
- 投放目标要明确表示是否接受、接受多少、结果是移动还是复制。
- 优先提供替代操作和撤销，因为拖放很容易误放，且对某些用户不可用。

### Web 做法与校验

- 可以使用 HTML5 Drag and Drop 或 Pointer Events；不要假设触摸、键盘和屏幕阅读器都有同等支持。
- 为每个可拖项目提供键盘可操作的“移动/排序/复制到”替代，且不依赖 hover 或右键。
- 明确 drag handle、可拖动区域和 drop zone；拖动时显示 ghost/placeholder、数量、接受状态和结果预览。
- 投放后维持选中状态和可撤销记录；如果跨页面/跨会话会复制，操作前说明。
- 不要用拖动作为排序的唯一方式；为长列表提供位置菜单、上下移动或批量操作。
- 处理 pointer capture、滚动自动扩展、软键盘、移动触控和浏览器文本选择冲突。

### Review 问句

- 没有鼠标或无法精确拖动时，用户还能完成同一任务吗？
- 用户能否在放手前预测结果是移动、复制、拒绝还是覆盖？
- 误放后能否撤销或把内容移回？

## Searching

### HIG 思想

- 如果搜索重要，应给它主位置和清晰范围；搜索行为应让用户知道正在搜什么。
- 一个主搜索入口通常比多个分散入口更容易发现；局部搜索应明确它只过滤当前视图。
- 最近搜索、自动完成和预测可提高效率，但要考虑隐私并提供清除方式。
- 搜索结果要处理无结果、拼写变化、范围变化和结果数量；搜索历史不应意外泄露。

### Web 做法与校验

- 使用 `role="search"`/`<search>` 或语义 form；输入有可见标签、清楚 placeholder，并支持清除和键盘提交。
- 当前 query、scope、filters 和排序尽量进入 URL；Back/Forward 与刷新后可恢复结果。
- 自动完成要有键盘操作、屏幕阅读器状态和错误处理；不要拦截浏览器 Find、复制粘贴或正常输入法行为。
- debounce 网络请求但保持本地反馈；显示“正在搜索”和“无结果”，不要让页面闪空。
- 搜索历史默认不公开显示，提供清除/不保存选项；敏感产品考虑关闭持久历史。
- Cmd/Ctrl+K、`/` 等快捷入口只能是额外方式，不能替代可见入口；避免劫持用户已有的系统/浏览器快捷键。

### Review 问句

- 用户能否在一眼内找到搜索，并知道搜索范围？
- 结果返回、无结果、网络失败和清空条件是否有稳定反馈？
- 刷新、分享链接和 Back 后能不能回到同一搜索上下文？

## Onboarding

### HIG 思想

- 最好的 onboarding 是让用户直接体验产品；需要时再教，不要一开始强迫读完。
- 交互式、逐个上下文的提示通常比一次性长 tour 更有效。
- 前置 onboarding 应短、有趣、可跳过、可稍后找到；不要要求用户记住大量信息。
- 非必要配置、权限、评分、购买应延后，先让用户看到价值。
- 不重复展示已经关闭或跳过的引导。

### Web 做法与校验

- 首次访问优先给可操作示例、示例数据或最小成功路径，再提供上下文提示。
- 允许跳过、关闭、重新打开；记忆状态不要依赖一次 session，除非用户明确选择。
- 逐个功能提示要锚定到真实控件，能键盘关闭，不阻塞页面；不要用遮罩层强迫用户按顺序点击。
- 权限在真正需要时请求，先解释原因和结果；不要把浏览器权限申请放在无上下文的首屏。
- 引导内容只讲本产品，不讲浏览器、系统或通用操作；控制文案长度和页数。
- 有教程时能让用户随时从帮助/设置返回，不在每次启动时重复弹出。

### Review 问句

- 用户能否跳过 onboarding 仍完成任务？
- 提示是否出现在用户需要它的上下文中，而不是一次性灌输？
- 关闭、跳过、稍后提醒和再次打开是否一致？

# Components

用于侧边栏、工具栏、Popover、菜单、列表与表格、图表的设计与 review。组件选型先问“用户当前要完成什么”，再问“用哪个 Web 组件”，不要先决定外观。

## Sidebars

### 适用场景

适合顶级区域、项目/工作区、文件夹或集合之间的长期导航；优点是层级可见、可扩展，代价是占用横向空间。

### HIG 判据

- 空间足够时才长期显示；空间不足时改用更紧凑的导航形式。
- 优先展示顶级区域，通常不超过两层；更深层级应交给内容列表或详情页。
- 支持折叠或隐藏，但默认应保持可发现；不要把入口藏到不可见手势后。
- 分组标签短而描述性；常用项目可让用户排序或配置。
- 选中态必须持续可见，并清楚表达当前位置。
- 避免把关键操作或信息放在侧边栏最底部，因为小窗口和浏览器 chrome 可能遮挡。

### Web 实现对照

- 使用 `<aside>` + `<nav>` 或独立 navigation landmark；不要用一组无语义 `div` 模拟。
- 宽屏可持久显示；中窄屏可折叠为图标 rail 或 drawer；最窄屏可用顶部导航或小型菜单。
- 用 container query 或布局状态决定折叠，不以设备品牌判断。
- 折叠后仍需保留当前上下文；drawer 打开后处理焦点、滚动锁定、`Esc` 和关闭后的焦点返回。
- 图标导航要有 tooltip/aria-label，并且与可见文字版本行为一致。

### Review 问句

- 这是“长期导航”还是“临时工具面板”？后者不应伪装成 sidebar。
- 折叠后用户还能知道自己在哪吗？
- 侧边栏是否因为宽度不足挤压主内容、图表或表格？

## Toolbars

### 适用场景

适合承载当前视图的标题、导航、高频动作和搜索；不是把所有命令都塞进一排图标。

### HIG 判据

- 命令要经过选择，避免拥挤；每个项目都应可区分并容易激活。
- 高优先级动作保持可见，低频动作进入 More/overflow；overflow 的顺序应反映优先级。
- 工具栏应帮助定位当前视图，而不是只堆按钮。
- 当空间不足时，应有明确的折叠/溢出策略，而不是让控件互相挤压。
- 控件分组要表达逻辑关系：导航、主操作、辅助操作分开。
- 不要用与内容同样抢眼的背景、颜色和文字样式覆盖内容。

### Web 实现对照

- 使用 `<header>` 或明确的 toolbar 区域；命令菜单用 `role="toolbar"` 或原生 button + menu 结构，按需实现 roving tabindex。
- 窄屏优先保留主操作与导航，次要操作进入 overflow；不要仅靠 CSS 隐藏而没有替代入口。
- 图标按钮必须有可达标签；有空间时优先显示文字，icon-only 要提供 tooltip。
- 固定 toolbar 应处理滚动、软键盘、safe area 和内容遮挡。
- 不要复制 macOS 交通灯按钮或 iOS 导航栏外观；Web 用户依赖浏览器和站点自己的导航习惯。

### Review 问句

- 工具栏是否只包含高频、和当前视图相关的动作？
- 窄屏时用户能否发现并执行次要动作？
- 主要动作是否被淹没在多个同权重按钮中？

## Popovers

### 适用场景

用于临时、锚定在某个控件旁的小范围内容或设置；适合快速查看/修改，不适合承载长流程或关键警告。

### HIG 判据

- 只显示少量相关信息或功能；内容应在用户完成短任务后自然结束。
- 位置靠近触发点，不要遮住触发元素或用户完成任务所必需的内容。
- 一次只显示一个 Popover；不要从 Popover 再打开 Popover 或层级链。
- 非模态 Popover 点击外部可能消失；自动关闭时不能丢失用户工作，除非用户明确取消。
- 关闭按钮只在需要确认/指导时使用；多选状态应保持到用户明确关闭。
- 不要用 Popover 显示需要用户明确处理的警告。

### Web 实现对照

- 优先使用 HTML Popover API 或 `<dialog popover>`；如果兼容性不足，可回退为有焦点管理的 `dialog` 或自定义层。
- 锚定位置可用 CSS anchor positioning 或 JS 计算，但必须处理视口边缘、滚动、缩放和键盘。
- 明确标记触发关系、关闭行为、`Esc`、点击外部和焦点返回；不要把 `aria-expanded` 状态遗漏。
- 小屏不要强行显示桌面 Popover；可改为底部 sheet 或全宽层，但仍要保留可理解的上下文。
- 模糊/阴影/箭头是附属视觉，不应代替层级和焦点管理。

### Review 问句

- 这是一个短任务还是完整页面？后者不应使用 Popover。
- 它是否有唯一触发点、单一层级、明确关闭和可恢复焦点？
- 在小屏和键盘操作下是否仍可用？

## Menus

### 适用场景

适合命令、选项、排序、筛选和当前状态切换；导航型链接列表应使用普通导航语义，不应为了样式都做成 menu。

### HIG 判据

- 每项标签短、明确；执行动作通常用动词/动词短语，状态项要说明当前状态。
- 禁用项仍应能被看到，让用户知道有哪些命令以及为什么可能不可用。
- 需要继续输入或选择才能完成的动作应显示省略号等提示。
- 分组表达相关命令；危险或不可逆命令要有隔离和明确反馈。
- 子菜单应少用，通常不超过一层，且子菜单中的项目数量要可控。
- 开关/状态项用勾选、单选或动态标签表达真实状态，不能只靠颜色。

### Web 实现对照

- 命令菜单可用 button + `aria-haspopup="menu"` + `role="menu"/menuitem`；普通站内导航应使用链接和 `<nav>`，不要滥用 ARIA menu。
- 支持方向键、Home/End、`Enter`、`Space`、`Esc` 与焦点返回；不要只支持鼠标 click。
- 快捷键可以在菜单中显示，但不要强加平台专属快捷键；Web 至少考虑 Cmd/Ctrl 的差异。
- 菜单不要无限滚动或成为 sitemap；过长时分组、搜索或将功能移到页面。
- 外部点击、滚动、路由变化时正确关闭，并避免关闭后状态不一致。

### Review 问句

- 用户读完标签能否预测结果？禁用和当前状态是否清楚？
- 是否有键盘路径、焦点可见和清晰的关闭行为？
- 是否能用更直白的分组或页面替代多级菜单？

## Lists and Tables

### 适用场景

列表适合层级、集合、导航和简单属性；表格适合具有明确列、可比较、可排序的多维数据。

### HIG 判据

- 行内容要短而可扫描；标题优先，元数据和操作次之。
- 多列表格使用描述性列头；不要让用户靠列位置猜含义。
- 选择列表项要有持续或明确的反馈；导航选择与临时选项选择的反馈方式应不同。
- 支持选择、编辑、排序、删除或重排时，行为要可见且可撤销；不要依赖隐藏手势。
- 行高、密度、截断和长文本策略应考虑真实数据，而不是理想样例。
- 复杂数据不要伪装成卡片网格；表格语义和比较关系不应被视觉改版破坏。

### Web 实现对照

- 表格数据使用 `<table>`、`thead`、`th`、`tbody`、`scope`、`caption`；如果没有真正的行列关系，不要为了样式使用 table。
- 排序、筛选、分页、选择、批量操作和空结果都要有可访问状态；排序按钮应表达当前排序方向。
- 长列表虚拟化时，不要把可访问语义、焦点顺序和屏幕阅读器项目数量破坏掉；必要时提供非虚拟化摘要或分页替代。
- 移动端可以改为卡片/堆叠布局，但保留字段标签、选择状态和操作可达性；不要只截取列。
- 行操作不要只出现在 hover；提供可见或键盘可达入口，危险操作与普通操作分离。

### Review 问句

- 用户能否快速找到关键列/字段，并比较行间差异？
- 长文本、空值、超大数字和本地化文本是否仍可扫描？
- 选择、排序、批量操作和空状态是否有一致反馈与恢复路径？

## Charts

### 适用场景

用于让用户理解趋势、分布、比较或异常，不是把所有数据点装饰成图。图表首先是信息产品，其次才是视觉组件。

### HIG 判据

- 图表需要有标题、必要说明、轴/单位、时间范围、图例或直接标注；不要让用户推断上下文。
- 以任务为中心选择图表类型；比较、趋势、部分与整体、分布和关系各有更合适的表达。
- 帮助用户发现变化；变化同时用动画和静态提示表达，确保关闭动效仍可理解。
- 图表与周围内容对齐；坐标、标签和标注不能互相遮挡。
- 不要只靠颜色区分数据系列；增加形状、线型、图案、直接标签或数据表。
- 交互元素要有足够命中区域，键盘/Switch/屏幕阅读器可按逻辑顺序读取；复杂数据要提供摘要或等价文本。
- 对数据变化、上限/下限、缺失值和空态给出明确说明，避免“空白图”被误读为零。

### Web 实现对照

- SVG 适合可缩放、可访问的统计图；Canvas 适合大数据/高性能绘制，但需额外维护语义、焦点和文本替代。
- 用 `<figure>` + `<figcaption>`、标题、单位、系列说明和可访问 summary；必要时提供 `<table>` 或下载数据。
- tooltip 是补充，不是唯一入口；hover/focus/键盘/触摸应都能查看重点值。
- 支持响应式布局、数据更新、窗口缩放和减少动态；避免动画导致坐标或读数跳变。
- 不要直接使用 Apple Charts / Swift Charts 的 API 形态或系统颜色；Web 图表需要自己的数据语义、色板和可访问实现。

### Review 问句

- 用户能否在没有 tooltip、没有颜色、没有动画时理解主要结论？
- 轴、单位、时间范围、缺失值和异常值是否明确？
- 是否有键盘与屏幕阅读器路径，且不会逐个朗读数千数据点？

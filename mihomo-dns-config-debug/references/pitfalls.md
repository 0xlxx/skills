# 五个坑与泄露检测

逐项对照「实际生效的配置」取证，而不是只看磁盘上的 YAML。命中的坑按改法修完，回到工作步骤 1 重走链路做回归。

## 坑一：名单与 policy 没同步

- **症状**：在 `nameserver-policy` 里给某个域名加了一行，想让它走指定 DNS，结果完全不生效。
- **根因**：fake-ip 模式下，不在名单里的域名先被发一个假 IP 打发走了，根本走不到策略匹配。
- **改法**：要让 `nameserver-policy` 对某个域名生效，就得让它同时上 `fake-ip-filter` 名单——两处一起加。名单里存在、但 policy 里没有的域名是正常的，它按后续 `nameserver` / `fallback` 流程解析。

## 坑二：配置搬到 Windows / macOS

- **症状**：非 Linux 平台下配置报错或行为异常。
- **根因**：`auto-redirect` 与 `route-exclude-address-set` 依赖 nftables，是 Linux 专属特性。
- **改法**：在非 Linux 平台把这两个参数删掉。

## 坑三：IPv6 流量从直连溜走

- **症状**：大量卡顿、断连，甚至 DNS 泄露。
- **根因**：配置里关了 IPv6，但设备开着 IPv6 时流量会优先走 IPv6，可能绕过代理直接出去。
- **改法**：IPv6 默认关闭；确有需求时采用主路由模式，并验证 IPv6 路径同样受代理和 DNS 规则控制。

## 坑四：浏览器自带的安全 DNS

- **症状**：fake-ip 不起作用，分流行为与配置不符。
- **根因**：浏览器 DoH 走 443 端口，53 端口的劫持抓不到它。这条 DoH 连接本身还是会进内核按规则走，但 DNS 查询已经绕开 mihomo 的 DNS 模块，浏览器直接拿到真实 IP。
- **改法**：关闭浏览器的安全 DNS，让查询回到 53 端口被内核接管。

## 坑五：软路由插件覆盖配置

- **症状**：最终生效的配置和预期不符，TUN 参数被改写、DNS 设置被替换。
- **根因**：OpenClash 一类插件启动时，界面上的全局配置优先级更高。
- **改法**：想拿到纯粹可控的效果就用裸核运行；使用插件时，核对最终运行配置与预期是否相符，或用插件的内核模式跑。

## 泄露检测为什么测不准

- **正规检测的思路**：用从未见过的随机子域名，逼着流量走遍整张规则表，尽可能覆盖所有解析情况，检验在没有任何规则匹配的盲区下到底会不会泄露。
- **假阴性**：现实中主流检测站的有些域名已经被国外规则收录，测试时直接域名出站，根本没机会进入盲区做检测——这就是不同站点结果不一致的原因。
- **怎么读结果**：「测出泄露」说明链路真的漏了。「没测出泄露」只能记为「无泄露证据」，先确认测试域名没被规则收录，再核对实际 DNS 查询出口。
- **反模式**：把泄露检测域名塞进代理规则来提高通过率，检测站看到的就不再是链路真实行为——这样做的同时要记录「该测试已不代表盲区路径」。

# 三类场景逐跳推演

承接 SKILL.md 的三类清单，这里只展开每类在 TCP / UDP 下的逐跳路径。

## 入口：53 端口被无差别接管

`tun.dns-hijack: ["any:53", "tcp://any:53"]` 把所有发往 53 端口的请求送进内核。客户端本地配了什么 DNS（哪怕是 223.5.5.5）都会被接管。

进内核后的第一件事：匹配名单（`fake-ip-filter`）——名单内不发假 IP。

## 第一类：国内域名

1. 命中名单里的国内域名集 → 跳过假 IP 分配。
2. 直接走 `nameserver-policy` 第一条国内规则 → 并发甩给阿里 + 腾讯的加密 DNS，采纳最快返回的结果。
3. 解析到此结束，下面的 `nameserver` 与 `fallback` 连看都不看。
4. 客户端拿到真实 IP 发起连接 → 命中 `route-exclude-address-set` 白名单 → 绕过内核直连，少一跳。
5. 删掉这条路由排除规则后，国内流量改为经内核转发、命中直连，面板也能看到连接状态。需要国内流量绕过内核时保留它，接受多一跳内核转发时删掉它。

**为什么用了 fake-ip 还要真实解析国内域名**：为了对上 `route-exclude-address-set` 白名单。假 IP 对不上白名单，就绕不过内核。

**映射表与 redir-host**：客户端每次查域名，内核返回 IP 时都会记一笔「这个 IP 对应哪个域名」。绕过大路时这张表用不上；流量进内核后，域名类规则主要靠它把真实 IP 还原成域名——这是 redir-host 的工作逻辑。

**嗅探的位置**：正常走内核 DNS 的流量本来就有域名，不需要嗅探。嗅探板块专门覆盖「没走内核 DNS 的纯 IP 流量」；`force-dns-mapping: false` 是这份配置作者的选择，避免对已有映射的域名重复嗅探——内核默认开启，保持开启同样能工作，只是会多做一次嗅探。整个板块删掉也不影响主线。

**UDP**：与 TCP 完全一样，国内这一类不用按协议区分看待。

## 第二类：国外域名（规则已收录）

### TCP

1. 进内核 → 不在名单里。
2. 内核不查真实 IP，直接从 fake-ip 地址池分配假 IP（如 `198.18.0.7`），映射表记一笔。
3. 本地零 DNS 查询、零等待。
4. 客户端拿假 IP 发起连接。开启 `auto-redirect` 时，TCP 由 nftables 直接重定向进内核，不经过 TUN 网卡；UDP 真的走 TUN。进内核之后处理一致。
5. 内核看到目标属于 fake-ip 网段 → 反查映射表还原真实域名。
6. 走分流规则命中对应规则集 → 走对应策略组 → 到出站。
7. 走支持域名封装的代理协议时，域名被塞进加密隧道发给境外落地节点，由落地节点完成真实解析，拿到离落地最近、最优的 CDN 地址。本地 DNS 查询始终为零。

### 不适合 fake-ip 的海外服务

STUN 打洞、NTP 对时、游戏联机、WiFi 通话这类应用会在本地校验 IP 合法性，拿到假 IP 直接报错。它们挂在 fake-ip 排除名单（`fakeipfilter_!cn` 规则集）里，走 `nameserver-policy` 第二条：指定默认代理去查 8.8.8.8，得到真实 IP。

**错位担心可以放下**：统一走默认代理查，而某个服务规则走美国节点、解析却用默认代理（可能在日本）——走代理的 TCP 不受影响。这次解析拿到的真 IP 纯粹用来给本地客户端做校验；客户端连接时内核反查映射表还原域名，发给落地节点的是域名，最终连哪个 CDN 由落地节点决定。

### UDP 的三种情况（按这个优先级判断）

先看第一条规则，再依次往下：`非 CN + UDP 443` 命中 REJECT 就结束；否则看域名在不在排除名单；都不在才进入双路判定。

**情况一：443/UDP 直接拒绝。** 浏览器访问流媒体时优先尝试 QUIC（UDP 443）。拿假 IP 进内核还原域名后，优先命中第一行阻断规则——海外域名 + 443 端口 + UDP 协议直接 REJECT。

掐掉的理由：QUIC 自带可靠传输，而 Trojan / VLESS 跑在 TCP 上，代理 UDP 相当于把它塞进 TCP 隧道，两层可靠传输叠在一起。丢一个包，外层重传一次，里面的 QUIC 等不到确认包也重传，多出来的数据又把隧道塞得更满，下一轮更容易超时，就这样滚下去。这就是 **TCP over TCP** 的熔断现象——别家网站都正常、唯独 YouTube 卡顿转圈，通常就是这里。Hysteria2 这类基于 QUIC 的协议机制不同、影响不大，但大多数协议都会受影响，直接禁掉最省事。

**情况二：在排除名单里的国外服务。** 它们本来就不走 fake-ip，走规则分流 → `nameserver-policy` 用 Google DNS 查到真实 IP → 直接拿这个 IP 发包（UDP 按 IP 出站）。

**情况三：既没被掐掉也没上排除名单。** 例如端口不是 443 的国外小众域名。客户端拿假 IP 进内核还原域名、命中外规则；因为要发 UDP，内核被迫在本地查一次真实 IP。它既不在国内集也不在排除名单，策略匹配不上，只能落到 `nameserver` 和 `fallback`。

## 第三类：未收录的小众域名

### TCP

1. 国内外规则集都没收录，也不在 fake-ip 排除名单 → 照样秒拿假 IP。
2. 拿假 IP 发起连接进内核 → 反查映射表还原原始域名。
3. 进入路由规则匹配：开头的私有 IP 规则挂了 `no-resolve`，直接跳过；中间一长串域名规则集一个都没命中。
4. 来到 IP 规则区。**真正让内核发起真实解析的是这里第一条不带 `no-resolve` 的 IP 规则**（配置里是 Google IP 规则）——为了判断这个未知域名到底算不算 Google 的 IP，内核必须在本地查一次真实 IP，而且全局只查这一次，后续所有 IP 规则直接复用结果。这条规则就是**探针**。
5. 这里最容易发生 DNS 泄露：如果这个冷门域名恰好是国外的，而默认解析 `nameserver` 填的是国内 DNS，内核为了对比 IP 规则就会向国内 DNS 发起解析——最典型的 DNS 泄露。
6. 正确做法：策略匹配不上后交由 `nameserver` 与 `fallback` 并发查询。

查出 IP 之后走哪条路，决定出站形态：

- 命中 IP 规则并走**代理** → 本地这个 IP 只用于匹配规则，出站发给落地节点的仍是原始域名（前提是代理协议支持域名封装）。
- 命中 `cn_ip` 等规则走**直连** → 由 `direct-nameserver` 重新解析，用解析出的 IP 建立连接。

### 双路判定

`nameserver` 与 `fallback` 都填 Google DNS、后面都挂默认代理（查询走指定代理出站），唯一区别是 `nameserver` 带了国内 ECS（`ecs=223.5.5.0/24`）。

带 ECS 的目的：走代理查询不加 ECS 时，Google 默认按海外落地节点位置返回 IP。如果这恰好是个国内冷门服务，就会拿到国外 IP，匹配不到国内 IP 规则，直接走兜底代理出站。加上国内 ECS 就是告诉 Google：如果该服务在大陆有节点，请按大陆网段返回国内 IP。

怎么辨别国内外——`fallback-filter` 拿 `nameserver` 查回的 IP 对比本地 GeoIP 数据库：

- **全是国内 IP** → 判定国内服务，采纳这个结果，命中后面的国内直连。这个结果只用来匹配规则，因为 CDN 不一定最优；真正建立直连出站时会再用 `direct-nameserver` 在本地干净地查一次，拿到真正适合本地宽带的最佳 CDN。
- **有一个是境外 IP** → 判定国外服务，弃用带 ECS 的结果，改用并发查回的 `fallback` 纯净结果去匹配 IP 规则。命中特定规则就进对应组；没命中就走兜底（漏网之鱼）走代理出站。

TCP 下本地查出来的海外 IP 不参与连接，所以纯 TCP 场景不配 `fallback` 也完全够用——`fallback` 是专门为 UDP 准备的，只是配了之后 TCP 也同样会走这个流程。

### UDP：为什么精度必须在本地解决

同样的未收录域名换成 UDP：第一行的海外 QUIC 规则拦不住它（端口不是 443），客户端拿假 IP 还原域名后一路到 IP 规则区，同样在探针处被迫发起本地真实解析。

最本质的差别在这里：

| 协议 | 本地查回的 IP 用来做什么 | 出站发什么 |
|---|---|---|
| TCP（走代理） | 只用来匹配规则 | 域名，随隧道发给落地节点 |
| TCP（走直连） | 匹配规则 | `direct-nameserver` 重新解析后的 IP |
| UDP | 直接用来发包 | 这个 IP 本身 |

所以 UDP 的解析准确性必须在本地解决。于是双路判定派上用场：ECS 结果判定不是国内 IP → 采纳并发查回的 `fallback` 纯净结果 → 内核拿这个精准的海外 IP 建立 UDP 连接。

## 视角对齐（原理与变体）

SKILL.md 的工作步骤 5 给出检查动作，这里解释为什么必须同视角。

`fallback` 后面挂的是默认代理，意味着 Google DNS 是按默认代理当前选中节点的位置去解析的。如果小众域名的兜底出站和解析节点不一致（解析用日本、兜底走美国），解析出的 IP 就谈不上准确。

所以兜底出站最好和 DNS 解析选同一个节点。最省心的做法：把「漏网之鱼」策略组直接选为默认代理，这样切换节点时两边自动同步。

在这套配置里，`fallback` 的唯一使命就是给走 UDP 的流量提供精准目标 IP。只优化 TCP 分流时可以省略 `fallback` 与 mmdb 数据库；需要 UDP 精确落地时两者都保留。省略 `fallback` 后内核仍有默认的后备解析行为，只是不如自定义的好用。

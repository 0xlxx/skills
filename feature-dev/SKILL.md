# feature-dev

新功能从需求到代码，分两个设计阶段和一个实现阶段。设计阶段产出方案文档，实现阶段按 DAG 拓扑序逐节点交付，每个节点完成即标记。

**递阶控制**贯穿设计：每个原子要素落在策略层、逻辑层、物理层之一。高层控制低层，低层不感知高层。DAG 的边从低层指向高层——低层产出的类型和数据，高层消费。

## 1. 设计方案

分析需求，产出设计文档。完成后再进下一步。

1. **需求概括** — 描述功能做什么、谁调用、触发条件。**完成标志**：概括短到能复述——读完即能回答做什么、谁用、何时触发。
2. **功能分解** — 识别构成这个功能的原子要素。一个原子要素是一个不可再分的职责——"验证邮箱格式"而非"处理用户输入"。**完成标志**：每个要素用一个动词短语命名，任两个要素的职责无交集——一个变更不会同时波及两个要素。
3. **分层** — 每个原子要素归入递阶控制三层之一：
   - **物理层**：数据存取、外部 I/O、基础类型——只做不做决策
   - **逻辑层**：业务规则、校验、变换——依赖物理层，不感知策略层
   - **策略层**：编排、协调、流程控制——依赖逻辑层和物理层，决定做什么、何时做
   **完成标志**：每个要素标注了层，依赖方向一致（策略→逻辑→物理）。反向依赖意味着低层要素在替高层做决策——回退修正。
4. **输出设计文档** — 写入 `design-{feature}.md`。按[设计文档格式](#设计文档格式)输出。**完成标志**：格式中所有必填段已填充，每个要素的三层归属已标注。

## 2. 实现方案

基于设计文档，为每个原子要素制定实现策略。完成后再进下一步。

1. **算法逻辑** — 每个原子要素的核心算法或数据流，用伪代码或要点描述。物理层要素描述 I/O 和数据形状；逻辑层要素描述变换规则；策略层要素描述编排流程。**完成标志**：每个要素有对应的算法描述。
2. **类型与约束** — 每个要素的输入输出类型签名、泛型约束（如适用）、不变量。**完成标志**：每个要素有类型签名，同一概念全链路用同一类型名——类型名不一致 = 同一概念多处定义，改一处漏另一处。
3. **测试策略** — 对每个要素，列出关键测试用例和 benchmark 目标（如适用）。物理层要素侧重边界值和错误路径；逻辑层要素侧重变换正确性；策略层要素侧重编排序列和失败回滚。**完成标志**：用例覆盖了该要素的契约边界（它承诺什么）和失败模式（它拒绝什么），不缺一个会出 bug 的路径。
4. **输出实现方案文档** — 追加到 `design-{feature}.md` 的 "实现方案" 节。**完成标志**：三个子节均已填充，类型签名可编译（不依赖尚未实现的要素）。

## 3. DAG 编排

识别原子要素间的数据依赖，形成 DAG，写入 TODO 跟踪系统。

1. **建图** — 每个原子要素是一个节点。若实现 B 需要 A 的产出（类型、数据、行为），则 A → B。物理层不依赖其他要素——它只产出，通常是源点；策略层只消费——它不产出被其他层需要的东西，通常是汇点。**完成标志**：每个要素在图中出现恰好一次，所有边表示真实的数据或控制依赖。
2. **拓扑排序** — 对 DAG 做拓扑排序，得到实现顺序。有环说明分层出错——低层要素暗中依赖了高层决策，回溯第 1 步修正。**完成标志**：拓扑序列覆盖所有节点，每个节点的依赖排在它之前。
3. **写入 TODO.md** — 在项目根创建 `TODO/` 目录和 `TODO/TODO.md`，按 [TODO.md 格式](TODO_TEMPLATE.md) 写入：活跃 DAG 可视化（ASCII 框图）和任务表格。每个任务标注层、依赖、状态（初始均为 ⬜）。**完成标志**：DAG 图与表格一致，每个节点的依赖列与图的入边一致。

## 4. 逐节点实现

按拓扑序逐节点实现。一次只做一个节点。

1. **取下一个待实现节点** — 拓扑序中第一个状态为 ⬜ 且所有依赖已完成的节点。**完成标志**：确定了当前节点。
2. **实现** — 写代码。**完成标志**：物理层实现完成时，其类型定义是调用方唯一需要知道的——类型即契约，无需读实现；逻辑层不重复定义物理层已有的类型；策略层不含领域逻辑，删掉它逻辑层和物理层仍各自正确。该节点的类型签名、实现、测试均已编写。
3. **验证** — 编译通过 + 该节点的测试全部通过。**完成标志**：针对该节点的测试绿了。
4. **标记完成** — 在 TODO.md 中将该节点状态改为 ✅。如果所有节点已完成，进入第 5 步归档。
5. **循环** — 回到步骤 1，直至所有节点 ✅。

## 5. 归档

全部节点完成后，将当前活跃 DAG 移入归档。

1. **概括** — 总结这批任务做了什么。**完成标志**：概括不超过一行。
2. **归档** — 将 TODO.md 的整个活跃板块原样复制到 `TODO/archive/{feature}-{date}.md`。在 TODO.md 的归档列表追加一行：`- [YYYY-MM-DD] {概括} → [archive/{file}.md](archive/{file}.md)`。清空活跃板块（仅保留空白的 DAG 图和表头）。**完成标志**：归档文件存在、内容完整，归档列表新条目格式正确，活跃板块已清空。

## 递阶控制三层

| 层 | 职责 | 依赖方向 | 典型例子 |
|----|------|----------|----------|
| 策略层 | 编排、协调、流程决策 | 依赖逻辑层和物理层 | Service、Workflow、Router |
| 逻辑层 | 业务规则、校验、变换 | 依赖物理层，不感知策略层 | Validator、Transformer、Domain |
| 物理层 | 数据存取、外部 I/O、基础类型 | 不依赖其他层 | Repository、Client、Model |

低层绝不引用上层——物理层 import 策略层 = 策略层改了签名，纯数据操作跟着崩，而它本不该知道策略层存在。

## 设计文档格式

```markdown
# {功能名称} — 设计方案

## 需求
{概括}

## 原子要素

### {要素 1 名称} — {物理层|逻辑层|策略层}
{职责描述}

### {要素 2 名称} — {层}
...

## 依赖关系
{ASCII 框图展示要素间数据流}

## 实现方案

### 算法逻辑
| 要素 | 算法/数据流 |
|------|-------------|
| ... | ... |

### 类型与约束
| 要素 | 类型签名 | 约束 |
|------|---------|------|
| ... | ... | ... |

### 测试策略
| 要素 | Happy Path | Edge Cases | Benchmark |
|------|-----------|------------|-----------|
| ... | ... | ... | ... |
```

## 约束

- 一个要素描述含 "并且"——它还是组合，继续识别其构成
- 低层引用上层——上层改签名导致纯数据操作崩掉，而它本不该感知上层
- 跳过设计直接写代码——结构边写边改，代价是返工
- 并行实现两个无依赖关系的节点——一个节点的 bug 污染另一个节点的验证，两个都白测
- TODO.md 批量更新——标记与实际状态脱节，TODO 失去跟踪意义
